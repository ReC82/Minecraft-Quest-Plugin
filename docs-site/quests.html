Quêtes

Implémentation : quest.QuestDefinitionParser (validation), quest.progress.QuestProgressEngine (progression en jeu). Un fichier par quête, dans plugins/RPGQuest/quests/*.yml.

Format

id: rpgquest:premiers_pas
title: "<gold>Premiers pas</gold>"
description: "<gray>Va faire connaissance avec le Libraire.</gray>"
category: intro
icon: BOOK              # optionnel, BOOK par défaut
giver: libraire          # optionnel — id du PNJ donneur (cf. /rpgadmin npc tag)
repeatable: true         # optionnel, false par défaut
cooldown: 20h            # optionnel, quête répétable seulement — délai avant de la refaire (30m, 20h, 1d)

prerequisites:            # optionnel — ids de quêtes déjà COMPLETED requises
  - rpgquest:autre_quete

steps:                     # obligatoire, ≥ 1
  - id: parler_au_libraire
    objectives:             # obligatoire, ≥ 1 par étape
      - type: TALK_TO_NPC
        npc: libraire

rewards:                    # optionnel
  - type: EXPERIENCE
    amount: 20

id, title, description, category, steps sont obligatoires. Une étape peut avoir plusieurs objectifs (tous requis) ; une quête peut avoir plusieurs étapes (dans l'ordre).

L'id d'une étape n'a besoin d'être unique que dans sa quête : deux quêtes peuvent chacune avoir un step_1. Il est enregistré dans la progression des joueurs : le renommer sur une quête publiée fait reprendre cette étape à l'étape 1. Dans PlugAdmin, il est généré automatiquement (step_1, step_2…) et ne se modifie que dans « Identifiant technique (avancé) ».

Types d'objectifs

TypeChampsDéclenché par
BREAK_BLOCKmaterial, amountCasser ce bloc. Le type du bloc lui-même : CARROTS pour des carottes plantées (pas CARROT).
PLACE_BLOCKmaterial, amountPoser ce bloc (type du bloc posé, ex. WALL_TORCH pour une torche murale).
KILL_ENTITYentity, amountTuer cette entité.
COLLECT_ITEMmaterial, amountRamasser cet objet au sol.
CRAFT_ITEMmaterial, amountFabriquer cet objet (établi ou grille de l'inventaire). Compte le nombre d'objets réellement fabriqués : 4 planches = +4, shift-clic = total rangé dans l'inventaire.
TALK_TO_NPCnpcClic droit sur le PNJ identifié avec cet id — voir la page PNJ. Toujours 1/1.
REACH_LOCATIONworld, x, y, z, radiusSe déplacer à moins de radius blocs (1.0 par défaut).
SMELT_ITEMmaterial, amount Cuire l'objet dans un four, un haut fourneau ou un fumoir. L'objet indiqué est celui qui sort du four. Obtenir l'objet autrement, ou le laisser sortir par un entonnoir, ne compte jamais.
DELIVER_ITEM_TO_NPCnpc, material, amount Remettre l'objet au PNJ, dans son dialogue. Collecter ou posséder ne compte jamais ; les objets sont réellement consommés. Dépôts partiels conservés.
DISCOVER_WAYPOINTamount, worlds (optionnel), count-mode (optionnel) Découvrir des waypoints distincts, en cliquant sur leur bouton. Passer à proximité, se téléporter ou recliquer un waypoint déjà connu ne comptent jamais. Deux waypoints du même biome comptent séparément ; renommer ou déplacer un waypoint ne le fait pas compter deux fois. worlds vide = tous les mondes. count-mode vaut NEW_ONLY (défaut : seules les découvertes faites pendant que l'objectif est actif) ou INCLUDE_EXISTING (les découvertes déjà acquises comptent aussi) ; la règle retenue est annoncée au joueur.
KILL_QUEST_BOSSmob (profil de boss, ex. ogre) Vaincre son boss de quête : un boss (profil de catégorie Boss, type « Boss de quête », activé) apparaît dans le Wild pour ce joueur quand l'étape commence. Le joueur reçoit le biome et le waypoint le plus proche (aussi dans son journal). L'objectif est rempli quand son boss meurt alors qu'il est à moins de 64 blocs ; tuer un autre mob ou le boss d'un autre joueur ne compte jamais. Abandonner la quête retire le boss (issue #171).
DISCOVER_CITYcity ou amount, count-mode (optionnel) Découvrir une ville précise (city, identifiant stable choisi par son nom dans PlugAdmin) ou amount villes distinctes. Seule la première entrée réelle dans une ville active compte (à pied, par téléportation ou à la connexion) ; y revenir, la renommer ou redémarrer ne compte jamais. count-mode : même règle que pour les waypoints, annoncée au joueur.

Onze types au total, aucun autre n'existe actuellement (pas d'objectif « utiliser un objet », par exemple).

Rapporter des objets à un PNJ (DELIVER_ITEM_TO_NPC). Le joueur dépose ce qu'il a, quand il l'a : 2 cuirs sur 4 font passer l'objectif à 2/4, les 2 cuirs sont consommés, et cette progression est définitivement acquise — elle survit à une mort, à une déconnexion et à un redémarrage du serveur. Il revient déposer le reliquat plus tard. Rien n'est jamais rendu.

Une même étape peut contenir plusieurs objectifs de remise (par exemple 1 bâton, 2 pierres, 4 cuirs, 3 graines). Une seule interaction avec le PNJ remet tout ce que le joueur possède d'utile : il ne clique pas une fois par matériau, et le serveur ne retire jamais plus que ce qui manque encore.

Côté dialogue du PNJ, il faut une branche avec la condition HAS_PENDING_DELIVERY et l'action DELIVER_QUEST_ITEMS — voir la page Dialogues. Un PNJ qui n'est destinataire d'aucun objectif actif ne peut rien accepter.

Types de récompenses

TypeChampsEffet
EXPERIENCEamountXP RPG (piste Globale), une fois par complétion — chat « + N XP RPG ». Seulement si progression.vanilla-xp-progression: true : XP vanilla (Player#giveExp). Issue #183.
ITEMmaterial, amountObjet vanilla donné.
VARIABLEkey, valueÉcrit une variable joueur persistante.
COMMANDcommandCommande console (%player% substitué). Aucune liste blanche ici.
HEARTamount (facultatif, 1), key (facultative)Ajoute durablement amount cœur(s) de vie maximum (2 PV par cœur, sans resource pack). Une seule fois par joueur et par clé de droit (par défaut la quête) : ni une quête répétable, ni une clé partagée entre plusieurs quêtes, ni un PNJ renommé ne le redonnent. Conservé après mort, reconnexion, redémarrage et reset joueur. Seuls les PV ajoutés sont remplis. Plafond facultatif : progression.max-bonus-hearts.
TABLEtable (identifiant d'une table de entitlements.yml)Tirage au sort d'une table de récompenses aléatoires (issue #177), une fois par complétion. Mode explicite de la table : « chances indépendantes » ou « une récompense maximum ». Le résultat est figé avec la fin de quête (jamais relancé) et remis comme un droit à récompense : inventaire plein = il attend. Table inconnue ou désactivée : le joueur voit « Tirage indisponible » ; récompenses désactivées sur le serveur : « récompenses aléatoires désactivées », aucun tirage. Les récompenses du catalogue (objets, enchantements, potions) et les tables se créent et se modifient dans PlugAdmin → Récompenses, y compris la création du catalogue lui-même et son activation (issue #474) — aucun fichier à écrire à la main ; l'éditeur de quête propose la liste des tables avec recherche.
MONEYamountCrédite le portefeuille persistant du joueur (même solde que /money, les marchands et le Control Panel). Aucun objet n'est donné : la monnaie est un solde, et aucun objet d'inventaire n'est compté comme de l'argent.

MONEY est crédité au plus une fois par complétion, et une récompense due n'est jamais perdue. À la remise, la complétion de la quête et une ligne de dette par récompense monétaire sont écrites dans la même transaction ; le paiement fait ensuite passer cette ligne de « due » à « payée » avec le crédit du portefeuille et la ligne de journal. Un arrêt brutal avant le paiement laisse donc une dette identifiable, reprise à la prochaine connexion du joueur avec la même identité de paiement — jamais un nouvel identifiant, donc jamais deux crédits. Une quête portant plusieurs récompenses MONEY les paie toutes, chacune ayant sa propre identité.

Le montant payé est celui enregistré à la complétion : rééditer la quête ensuite ne change pas une dette déjà née. Le moteur n'impose aucun plafond au montant (c'est une décision d'équilibrage) ; l'éditeur du Control Panel se contente d'avertir au-delà d'un million, pour attraper la faute de frappe. Les reprises sont bornées : une relecture par chargement de joueur, et au-delà de quelques échecs la récompense attend une action d'administrateur plutôt que d'être réessayée indéfiniment.

Notifications de progression

Implémentation : quest.progress.QuestProgressEngine#showQuestStarted / #showObjectiveProgress / #showQuestCompleted. Démarrage, progression et fin restent hors du chat pour ne pas le spammer ; la fin d'une quête envoie en plus un court résumé dans le chat listant ce qui a été réellement reçu :

ÉvénementCanalContenu (exemple)
Quête démarréeTitle/Subtitle plein écran, bref (~3 s)« Quête commencée » / « Premiers pas »
Objectif qui progresseActionBar (se remplace en place)« Parler à libraire 1/1 »
Quête terminéeTitle/Subtitle plein écran, bref (~3 s)« Quête terminée » / « Premiers pas »
Récompenses de la remiseChat, une fois, seulement si la quête donne quelque chose« Quête terminée : Premiers pas — récompenses : »
« + 20 XP »

Le texte de ces notifications est entièrement personnalisable dans messages.yml (quest.started-title/started-subtitle, quest.objective-progress, quest.completed-title/completed-subtitle, quest.reward-summary-header/reward-line-experience/reward-line-item/reward-line-special), rechargé par /quest admin reload — jamais un titre de quête codé en dur : le nom affiché vient toujours du title: de la quête concernée. L'ActionBar se déclenche à chaque incrément d'objectif, qu'il complète l'objectif ou non (ex. 1/2 puis 2/2 pour tuer deux zombies) — y compris quand l'action de dialogue ADVANCE_QUEST force la complétion (voir Dialogues). Le résumé chat n'affiche que les récompenses réellement accordées par cette quête précise (une ITEM affiche l'objet et la quantité donnés, une EXPERIENCE l'XP donnée ; une récompense COMMAND — ex. objet spécial livré via /customitem give — affiche une ligne générique « Récompense spéciale » car le contenu d'une commande arbitraire n'est pas inspectable ; une VARIABLE n'affiche rien, c'est un état interne du plugin, pas quelque chose que le joueur reçoit). Le journal de quêtes (/quests) continue, lui, d'afficher les récompenses prévues pour n'importe quelle quête, même non commencée.

Inventaire plein (issue #318) : la remise n'a lieu que si toutes les récompenses d'objets (ITEM et COMMAND customitem give) tiennent dans l'inventaire — rien n'est jamais jeté au sol ni accordé à moitié. Objectifs remplis mais pas de place : la quête passe « Prête à remettre » (READY_TO_TURN_IN), le joueur est prévenu une fois, et elle se termine d'elle-même dès qu'il a libéré de la place (inventaire fermé, objet jeté, reconnexion). Une remise demandée à un PNJ (TURN_IN_QUEST) ou par l'administration est simplement refusée, quête inchangée, à retenter.

Une récompense MONEY ne figure pas dans ce résumé : son crédit est asynchrone, et une ligne écrite à cet instant annoncerait un gain avant toute preuve qu'il a eu lieu. Son message arrive donc séparément, un court instant plus tard, et seulement après la réponse de la base (quest.reward-money-credited, qui cite le montant et le nouveau solde relu en base). Si le crédit échoue, quest.reward-money-failed le dit explicitement — jamais un faux succès, jamais un silence. Les deux passent par le chat et jamais par l'ActionBar, réservée à la progression des objectifs.

Le journal de quêtes affiche aussi la bourse du joueur (emplacement inerte de la barre du haut, en liste comme en vue détail) : le solde réel y est lisible sans connaître /money, et il est relu après chaque transaction. En cas d'erreur de lecture, la bourse affiche « indisponible » plutôt qu'un 0 trompeur.

Progression RPG (#183) : dans la liste, la bourse porte aussi le niveau RPG global et sa jauge ; un clic dessus ouvre la page « Ma progression RPG » — une jauge par piste (Global, Combat, Minage, Agriculture, Pêche, Exploration) : niveau, XP courante / requise pour le niveau suivant, pourcentage, « Niveau maximal atteint ». Lecture seule, sans commande à taper ; « Retour » ramène à l'onglet d'origine. Dans la vue détail d'une quête, la bourse reste inerte.

Quêtes renouvelables (#13) : dans « Quêtes terminées », une quête repeatable affiche « À refaire dans 19 h 40 min » tant que son cooldown court, puis « Peut être refaite ». Une quête de rencontre (catégorie encounter) porte aussi l'étiquette « Rencontre — quête secondaire ». La vue détail indique la cadence (« toutes les 20 h »).

Quêtes quotidiennes et hebdomadaires (#15)

Une quête portant period: daily ou period: weekly est un modèle : jamais proposée par un PNJ, un catalogue ou /quest accept. Dès que le joueur a ouvert son journal une première fois, le plugin lui attribue chaque jour daily-count quêtes quotidiennes et chaque semaine weekly-count hebdomadaires (en évitant celles de la période précédente), et les démarre. Elles se lisent dans les onglets « Quêtes quotidiennes » (horloge) et « Quêtes hebdomadaires » (boussole) du journal, avec le temps restant avant les nouvelles quêtes.

Réinitialisation à periodic-quests.reset-time (04:00 par défaut) dans le fuseau periodic-quests.timezone (Europe/Paris), la semaine changeant le weekly-reset-day (lundi). Une quête non finie à temps expire sans récompense ; une quête finie ne rapporte qu'une fois par période. repeatable: false, cooldown et prerequisites sont refusés sur un modèle périodique.

Dans le journal, le titre de l'onglet affiche l'avancement (« Quotidiennes : 1/2 terminée ») et les quêtes sont rangées en deux rangées : « À faire » (vitre jaune) puis « Terminées » (vitre verte, quêtes brillantes), comptées sur les quêtes réellement attribuées au joueur. Dans PlugAdmin, la page Quêtes a des onglets « Quotidiennes » et « Hebdomadaires » : modèles, réglages du serveur en lecture seule, bouton de création préréglé.

Exemple complet : Guide → Libraire

La quête rpgquest:premiers_pas, livrée avec le plugin, illustre l'enchaînement complet PNJ → dialogue → quête → dialogue → récompense. Trois fichiers, tous dans plugins/RPGQuest/ : 

# dialogues/guide.yml — le PNJ "Guide" (id RPGQuest : guide) démarre la quête
id: rpgquest:guide
start: greeting
nodes:
  greeting:
    speaker: "Guide"
    text: "<white>Bienvenue au village !</white> <gray>Va donc voir notre libraire, il pourra t'aider.</gray>"
    choices:
      - text: "Très bien, j'y vais."
        conditions:
          - type: QUEST_STATE
            quest: rpgquest:premiers_pas
            state: NOT_STARTED
        actions:
          - type: START_QUEST
            quest: rpgquest:premiers_pas
      - text: "Non merci."
        actions:
          - type: CLOSE

# quests/premiers_pas.yml — un seul objectif : parler au PNJ id "libraire"
id: rpgquest:premiers_pas
title: "<gold>Premiers pas</gold>"
description: "<gray>Va faire connaissance avec le Libraire.</gray>"
category: intro
icon: BOOK
repeatable: true
steps:
  - id: parler_au_libraire
    objectives:
      - type: TALK_TO_NPC
        npc: libraire
rewards:
  - type: EXPERIENCE
    amount: 20

# dialogues/libraire.yml — id "rpgquest:libraire" = id RPGQuest "libraire" du PNJ :
# cliquer sur ce PNJ satisfait automatiquement l'objectif TALK_TO_NPC ci-dessus
id: rpgquest:libraire
start: greeting
nodes:
  greeting:
    speaker: "Libraire"
    text: "<white>Ah, le Guide t'envoie ?</white> <gray>Bienvenue !</gray>"
    choices:
      - text: "Merci !"
        actions:
          - type: CLOSE

Déroulé en jeu : clic droit sur le PNJ « Guide » (id RPGQuest guide) → choix « Très bien, j'y vais. » → START_QUEST accepte rpgquest:premiers_pas (Title « Quête commencée ») → clic droit sur le PNJ « Libraire » (id RPGQuest libraire) → l'objectif TALK_TO_NPC npc: libraire passe à 1/1 (ActionBar) → l'étape est la seule de la quête, donc elle se termine aussitôt (Title « Quête terminée », 20 XP accordée) → le dialogue du Libraire s'affiche normalement, indépendamment de la quête.

Les deux PNJ doivent être identifiés au préalable avec /rpgadmin npc tag guide et /rpgadmin npc tag libraire (voir PNJ) — l'id RPGQuest du PNJ, l'id (sans namespace) du dialogue, et le champ npc: de l'objectif doivent tous les trois correspondre exactement.

Workflow : créer une nouvelle quête sans Claude

Procédure manuelle complète, sans aucun outil externe — juste un éditeur de texte et le serveur.

  1. Choisir un id unique (minuscules, chiffres, _/-) et une category — voir le tableau Format ci-dessus pour les champs obligatoires.
  2. Créer le fichier plugins/RPGQuest/quests/<id>.yml (en développement local : run/plugins/RPGQuest/quests/) avec id, title, description, category, au moins un step contenant au moins un objectif du tableau Types d'objectifs ci-dessus.
  3. Si un objectif est TALK_TO_NPC : identifier l'entité/PNJ correspondante avec /rpgadmin npc tag <id> (le <id> doit être exactement celui utilisé dans npc:) — voir PNJ.
  4. Ajouter des rewards si voulu, uniquement parmi les types du tableau Types de récompenses ci-dessus.
  5. Vérifier la syntaxe sans rien appliquer : /quest admin validate — corriger toute erreur signalée avant de continuer.
  6. Appliquer à chaud : /quest admin reload — pas besoin de redémarrer le serveur pour une quête (contrairement à un dialogue).
  7. Tester : /quest accept <id>, réaliser l'objectif en jeu, vérifier la progression avec /quest progress <id>, confirmer la remise (Title « Quête terminée » + récompenses reçues).
  8. Pour rejouer pendant les tests sans attendre : /quest admin reset <joueur> <id> (voir Outils admin de test) — fonctionne même si repeatable: false.

Commandes

# Joueur (permission rpgquest.quest)
/quest list
/quest accept <id>
/quest progress [id]
/quest abandon <id>
/quests                       # journal graphique (menu paginé) : toute quête acceptée, dépôts remis/demandés,
                              # étiquette « Amélioration du kit — palier N » sur les quêtes de palier (#475)

# Admin (permission rpgquest.admin)
/quest complete <id>         # force la complétion, soi-même uniquement
/quest admin reload            # recharge quêtes + messages, à chaud
/quest admin validate          # valide sans appliquer
/quest admin reset <joueur> <id|all>   # réinitialise une/toutes les quêtes d'un joueur en ligne
