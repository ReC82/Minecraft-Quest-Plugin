## Demande

Finaliser un vrai socle RBAC pour le Control Panel (PlugAdmin), en **consolidant l'existant** et
sans repartir de zéro. Modèle cible : `utilisateur → rôle(s) → permissions explicites → contrôle
backend → UI adaptée`. Les modules doivent vérifier des permissions, jamais un `if role == OWNER`
dispersé. Points clés du cahier des charges :

1. Auditer l'existant (modèle User, stockage, rôles, enum `Permission`, mapping rôle→permissions,
   `AuthorizationService`/`can(...)`, contrôles de routes et d'AgentAction, navigation
   conditionnelle, audit, hachage de mot de passe, actif/inactif, `if OWNER` dispersés).
2. Rôles représentables : `OWNER`, `ADMIN`, `TESTER`, `BUILDER`, `CONTENT_EDITOR`, `READ_ONLY` —
   propres à PlugAdmin, aucune correspondance automatique avec OP / Paper / LuckPerms.
3. Conserver les permissions existantes, ne pas renommer massivement ; `OWNER` obtient toutes les
   permissions automatiquement (`allOf`), pas de liste à maintenir.
4. Matrice de rôles cohérente à partir des permissions **réellement présentes** — ne pas inventer
   de permissions sans usage réel.
5. Page OWNER de gestion des utilisateurs (`/users`) : voir / créer / changer de rôle /
   activer-désactiver ; motif liste compacte → clic → détail, mobile.
6. Mot de passe : jamais en clair, hachage actuel audité et conservé s'il convient, jamais
   réaffiché ni journalisé.
7. Sécurité des mutations : permission dédiée, contrôle backend, CSRF, audit, validation serveur ;
   requête directe sans permission → 403.
8. Protection du OWNER : impossible de désactiver / rétrograder le dernier OWNER actif ou de se
   verrouiller hors du panel.
9. Navigation adaptée aux permissions, backend toujours protégé, afficher l'utilisateur et le
   rôle courant, 403 humain.
10. Audit : création, activation/désactivation, changement de rôle, refus sensibles.
11. Pas de permissions par environnement / serveur / temporaires / 2FA / SSO maintenant, mais ne
    pas fermer l'architecture à ces évolutions.
12. Tests ciblés (OWNER tout + gestion users ; ADMIN sans gestion users ; TESTER sans déploiement ;
    BUILDER sans données joueurs ; CONTENT_EDITOR édite mais ne déploie pas ; READ_ONLY aucune
    mutation ; route interdite en appel direct → 403 ; création / hash / changement de rôle /
    désactivation / dernier OWNER / CSRF / audit ; utilisateur désactivé ne peut plus utiliser sa
    session ; navigation reflète les permissions). Puis `:control-panel:test` / `test` / `build`
    verts.
13. Migration Control Panel si nécessaire : explicite, idempotente, testée, sauvegarde avant
    déploiement ; aucun changement `data.db` RPGQuest ; aucune migration MariaDB (#42).
14. Déployer **uniquement** le Control Panel AWS (`scripts/plugadmin/deploy.sh`), vérifications
    post-déploiement.
15. Fournir une checklist de validation navigateur courte.
16. Hors périmètre : permissions Paper / LuckPerms, #27 builder in-game, 2FA, SSO, OAuth,
    permissions PROD/DEV avancées, workflow d'approbation, refonte globale PlugAdmin, #42. Ne pas

## Analyse

### Audit de l'existant (avant intervention)

| Élément | État trouvé |
|---|---|
| Modèle User | **Aucun** — un seul `owner` en dur (`AuthService(ownerUsername, ownerPasswordHash, hasher)`), identifiants lus de l'environnement. |
| Stockage utilisateurs | Inexistant. `control-panel.db` (SQLite) contenait `audit_log`, `agent_heartbeat`, `agent_action`. |
| Enum `Permission` | Présente (`panel.authz.Permission`, ~26 valeurs déjà utilisées par les modules). |
| Enum `Role` | Présente : `OWNER`, `TESTER`, `CONTENT_EDITOR`, `READ_ONLY` — `OWNER` = `EnumSet.allOf`. Pas de `ADMIN` ni `BUILDER`. |
| Mapping rôle → permissions | Présent dans `Role` (constructeur avec `EnumSet`). |
| `AuthorizationService` | `PermissionService.can(roleName, Permission)` — déjà centralisé, déjà utilisé par tous les handlers de pages métier et par la création d'AgentAction (`AgentActionCatalog.Spec#permission()`). |
| Contrôles de routes | Chaque handler `PanelApp` faisait `permissions.can(session.role(), …)` puis un `Http.html(403, …)` **inline** (message hétérogène, parfois avec le nom d'enum). |
| Contrôle AgentAction | `AgentActionCatalog` : chaque type porte sa `Permission`, re-vérifiée à la création. |
| Navigation conditionnelle | `HomePages` filtrait déjà ses tuiles par permission. `Layout.nav()` **non filtré** (statique). |
| Audit | `AuditLog` append-only (`SqliteAuditLog` / `InMemoryAuditLog`), `login.success` / `login.failure` / `logout` / `agent.action.*` / `*.content.write`. |
| Hachage mot de passe | `PasswordHasher` PBKDF2-HMAC-SHA256, 210 000 itérations, sel 16 o, dérivé 256 bits, `MessageDigest.isEqual` (temps constant). **Fort et approprié — conservé.** |
| Actif / inactif | Inexistant (un seul compte). |
| `if OWNER` dispersés | Aucun trouvé — le projet passait déjà par `PermissionService`. Le vrai manque : pas de comptes, pas de rôles `ADMIN`/`BUILDER`, pas de page de gestion, nav non filtrée, 403 hétérogènes. |

### Ce qui manquait réellement à #50

- Le rôle `ADMIN` et le rôle `BUILDER`.
- Une permission `USER_MANAGE` (aucune permission de gestion des comptes n'existait).
- Un modèle de compte + stockage + amorçage du OWNER + actif/inactif.
- `AuthService` adossé à ce stockage (au lieu d'un unique compte en dur).
- Un re-contrôle de session par requête (compte désactivé / rôle changé).
- La page `/users` + ses mutations sécurisées.
- Le filtrage de `Layout.nav()` et l'affichage du rôle courant.
- Une page 403 unique et humaine.

Aucune permission fonctionnelle n'a été renommée. Aucune permission « pour remplir la matrice »
n'a été créée (seul `USER_MANAGE` est ajouté, avec un usage réel : la page `/users`).

   Minecraft.
2. **`authz.Role`** — ajout de `ADMIN` et `BUILDER` ; matrice complète reconstruite à partir des

6. **`security.Session`** — ajout `userId` ; `role` devient `volatile` + `refreshRole(String)`

## Limitations / travail restant

- **MVP mono-rôle par compte** : le modèle stocke un rôle unique. Multi-rôles, permissions par
  environnement / serveur / module, droits temporaires, approbation à deux niveaux,
  groupes/équipes, 2FA, SSO/OAuth, invitations, reset de mot de passe self-service : **hors
  périmètre #50**, volontairement non implémentés — l'architecture (`Role` → `Set<Permission>`,
  `PermissionService.can`, table `panel_user`) ne les bloque pas.
