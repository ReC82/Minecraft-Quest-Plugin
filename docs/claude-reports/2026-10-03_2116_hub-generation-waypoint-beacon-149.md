## Analyse

Relecture de #149 et des décisions #136/#137 actualisées : le Hub (`hub.world`, concrètement
`world_hub`) est désormais un monde explorable à part entière où les waypoints/bornes peuvent se
générer, à l'exclusion stricte des claims. Le mécanisme de génération par instance de biome existe
déjà intégralement pour le Wild (`waypoint.WaypointService`, issue #124) : identité d'instance
(`WaypointIdentityResolver`/`BiomeInstanceKey`), recherche de candidats déterministe
(`WaypointGenerationPlanner`), recherche de surface sûre (`RandomSafeLocationFinder`), verrou
mono-vol + retry borné, persistance idempotente par `(world, biome_instance)`. Décision de
conception : **réutiliser ce mécanisme tel quel**, jamais le dupliquer/réécrire, en l'exposant via
une nouvelle méthode publique (`ensureGenerated`) appelable depuis `travel.beacon` plutôt que de
coupler `WaypointService` à `TravelBeaconService` par un callback — `handleMovement` (le chemin
Wild) reste **strictement inchangé**, aucun risque de régression sur le mécanisme déjà testé et en
production.

La borne, elle, n'a jamais eu de mécanisme de génération automatique (#132/#150/#151 ne l'ont posée
qu'administrativement). Décision : un second mécanisme **symétrique** (verrou mono-vol, retry
borné, index par instance) vit dans `TravelBeaconService`, piloté par un poll sur chaque déplacement
Hub throttlé — si le waypoint associé n'est pas encore prêt (génération asynchrone), l'appariement
réessaiera naturellement au prochain déplacement d'un joueur dans cette instance (le sien ou celui
d'un autre), sans scan supplémentaire ni nouvelle dépendance croisée entre les deux services.

## Travail effectué

**Configuration** (`config.TravelConfig`) :
- `WaypointConfig` +`hubEnabled` (9e composante ; constructeur de compatibilité à 8 arguments
  conservé, défaut `true` — décision actée remplaçant l'exclusion historique du Hub).
- Nouveau `BeaconConfig` (`buttonMaterial`, `hubGenerationEnabled`, `pairMinSpacing`,
  `pairMaxSpacing`), `TravelConfig` passe de 4 à 5 composantes (constructeur de compatibilité à 4
  conservé, défaut `BeaconConfig.defaults()` = `OAK_BUTTON`/`true`/6/16).
- `ConfigValidator#validateBeacon` (nouveau) : `button-material` doit finir par `_BUTTON`,
  validation `positiveInt` pour les espacements, `max >= min`.
- `config.yml` : `travel.waypoint.hub-enabled: true`, nouvelle section `travel.beacon.*`.

**Waypoint** (`waypoint.WaypointService`) :
- Nouvelle méthode publique **additive** `ensureGenerated(World, Location)` : exactement le corps
  de recherche/génération de `handleMovement`, exposée pour un appel externe (Hub) sans throttle ni
  notion de « dernier joueur/instance » propre au Wild — `handleMovement` n'est touché par aucune
  ligne de ce changement.

**Borne** (`travel.beacon`) :
- `TravelBeacon` +`biomeInstance` (compact constructor normalise `null`→`""`),
  `isAutoGenerated()` = `!biomeInstance.isBlank()`.
- `TravelBeaconRepository#findByInstance(world, biomeInstance)` (nouveau, réalignement en cas de
  course perdue, même patron que `WaypointRepository#findByInstance`).
- `TravelBeaconService` étendu : constructeur +2 dépendances (`Supplier<TravelConfig>` déjà
  présent, `Supplier<String> hubWorld`) ; `handleHubMovement(Player, Location)` (nouveau, appelé par
  `TravelBeaconListener#onMove` sur `PlayerMoveEvent`, filtré `hub.world` + `travel.waypoint.hub-
  enabled`, throttlé comme le Wild) → appelle `WaypointService#ensureGenerated` puis, si le
  waypoint de l'instance est déjà présent, `ensureBeaconPaired`/`attemptPairBeacon` (recherche
  d'anneau autour du waypoint, `pairMinSpacing..pairMaxSpacing`, jamais à la même position, respect
  des constructions/zones protégées existantes via les mêmes gardes que le placement administré) →
  persistance avec `biomeInstance` renseigné. `placeAt()` (placement administré, Wild) lit
  désormais le matériau de bouton **configuré** au lieu d'un `Material.OAK_BUTTON` en dur, et pose
  toujours `biomeInstance=""` (`isAutoGenerated()==false` — jamais confondu avec une génération
  Hub).
- `TravelBeaconListener` : nouveau `onMove(PlayerMoveEvent)` (changement de bloc horizontal
  seulement, même garde-fou que `waypoint.WaypointListener`).

**Schéma** : migration **V21** — `ALTER TABLE travel_beacons ADD COLUMN biome_instance TEXT NOT
NULL DEFAULT ''`, idempotente (`dialect.columnExists`), `CURRENT_VERSION` 20→21. Décision : ajouter
une migration V21 plutôt que de modifier la V19 déjà écrite, même si celle-ci n'a jamais été
déployée nulle part — cohérence avec le patron idempotent déjà établi (V14/V15) pour toute
évolution de schéma, sans exception.

**Bootstrap** : `RPGQuestBootstrap` — construction de `TravelBeaconService` étendue aux 2 nouvelles
dépendances (`() -> configService.current().travel()` déjà présent, `() -> configService.current().
hub().world()` nouveau).

1. Génération progressive : un déplacement Hub déclenche la génération du waypoint (asynchrone, pas
   encore de borne) ; un second déplacement (par un autre joueur, simulant une visite ultérieure une
   fois le waypoint prêt) apparie une borne **distincte** du waypoint (positions différentes
   vérifiées) ; rejouer plusieurs fois (autres joueurs, mouvements répétés) ne crée jamais de second
   waypoint ni de seconde borne.
2. Deux instances de biome du Hub séparées (offset `4 × region-size`, même patron que le test
   équivalent de `WaypointServiceTest`) obtiennent chacune sa propre paire waypoint+borne,
   `biomeInstance` distincte.
3. `travel.waypoint.hub-enabled=false` : aucune génération, ni waypoint ni borne, même dans le Hub.
4. `travel.beacon.hub-generation.enabled=false` : le waypoint se génère seul, aucune borne n'est
   jamais appariée.
5. `handleHubMovement` appelé avec une position **hors** du monde Hub configuré : aucun effet ;
   `placeAt()` (placement administré Wild) confirmé `isAutoGenerated()==false`.
6. Protection : après génération+appariement Hub, `waypointService.isProtectedBlock` et
   `service.isProtectedBlock` couvrent bien les deux nouvelles structures.
